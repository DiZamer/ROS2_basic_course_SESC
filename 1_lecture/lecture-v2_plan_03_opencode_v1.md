# Занятие 3 — план lecture-v2: агентная инженерия с OpenCode

> Содержание: [`lecture-v2_content_03_opencode_v1.md`](lecture-v2_content_03_opencode_v1.md). Слайды: [`../1_slides/lecture-v2_slides_03_opencode_v1.md`](../1_slides/lecture-v2_slides_03_opencode_v1.md).

## Цель и результаты

Студент выполняет первый запрос к агенту, проверяет его права и умеет подтвердить ответ содержимым файлов. В конце он объясняет, почему инструкция `AGENTS.md` не заменяет permissions и почему результат всё равно проверяет человек.

## Подготовка преподавателя

- Проверить OpenCode и провайдера заранее; команда версии и agent list должны работать.
- Открыть корневой `opencode.jsonc`, `AGENTS.md`, README TIAGo и список пакетов.
- Проверить, что занятие проводится на тестовой папке/безопасном read-only вопросе. Не сравнивать Plan и Build на рабочем TIAGo через правки.
- Убедиться, что в projected prompt нет ключей, `.env`, токенов или личных данных.
- Если OpenCode недоступен из-за провайдера — иметь снимок заранее подготовленного ответа и исходные файлы для ручной сверки.

## Структура 40 + 40 + 40

| Время | Уровень | Результат |
| --- | --- | --- |
| 0–40 | Лекция | Студент понимает запрос, контекст, инструменты и права. |
| 40–80 | Практика | Выполнен read-only цикл в тестовой папке, ответ подтверждён файлами. |
| 80–120 | TIAGo | Агент помог найти факт о проекте робота, студент сверил его по источнику. |
| После | ДЗ | Добавлена проверенная заметка к личной модели. |

## Уровень 1 — лекция, 0–40 минут

| Минуты | Блок | Объяснить и показать | Проверка |
| --- | --- | --- | --- |
| 0–5 | Вызов | Нужно понять чужой пакет TIAGo без чтения всего workspace. | «Достаточно ли попросить: объясни робота?» |
| 5–11 | Что такое агент | Запрос → контекст → выбор следующего шага → инструменты → ответ. | Отличить агента от обычной справки/поиска. |
| 11–18 | Запрос как техническое задание | Цель, разрешённый контекст, ограничения, формат, проверка. | Переформулировать общий запрос в проверяемый. |
| 18–25 | Инструкции | Роль `AGENTS.md`, project config и правила провайдера. | «Если инструкция говорит read-only, значит ли это технический запрет?» |
| 25–32 | Permissions и агенты | Объяснить `allow/ask/deny`; сравнить предполагаемые роли Plan/Build, подчеркнуть зависимость от конфигурации. | Найти `edit`/`bash` в текущем `opencode.jsonc`. |
| 32–37 | Проверка факта | Показать ответ со ссылкой на файл, открыть файл и сверить. | Что считать доказательством ответа? |
| 37–40 | Выходной билет | Секрет, команда на изменение, неверный путь — выбрать безопасный шаг. | Студент называет наблюдение и проверку прежде действия. |

### Реплики преподавателя

- «Агент — быстрый помощник, а не источник истины».
- «Инструкция сообщает цель; permission ограничивает инструменты. Это разные вещи».
- «Попроси указать файл и место, где ответ подтверждается».
- «Название Plan само по себе не доказывает, что конфигурация read-only».

### Показать плохой и хороший prompt

Плохой: «Расскажи про робота».

Хороший: «Открой README в `3_Robot/TIAgo_humble`; перечисли базовый ROS-дистрибутив и команду запуска симуляции; ничего не меняй; приведи пути к двум подтверждающим строкам».

## Уровень 2 — практика, 40–80 минут

Инструкция: [`../2_practice/practice-v2_03_opencode_v1.md`](../2_practice/practice-v2_03_opencode_v1.md).

| Время | Шаг | Действие | Контроль |
| --- | --- | --- | --- |
| 40–45 | Проверить инструмент | `opencode --version`, `opencode --help` | CLI доступен; конфигурация провайдера не показывается на экране. |
| 45–52 | Прочитать конфигурацию | Найти `agent`, `permission`, `instructions` в `opencode.jsonc`. | Студент различает инструкцию и право инструмента. |
| 52–60 | Сформулировать запрос | Запрос о небольшой тестовой папке с явным read-only ограничением. | Есть цель, контекст, запрет изменений и формат результата. |
| 60–68 | Выполнить запрос | Использовать Plan/режим исследования, предварительно сверив права. | Агент указал файлы, ничего не изменил. |
| 68–74 | Проверить утверждения | Открыть названные файлы; сравнить вывод с источником. | Хотя бы один вывод имеет подтверждение в файле. |
| 74–80 | Exit ticket | Записать точность, полезность и одно ограничение. | Студент знает, что именно проверил. |

Практика запускается на тестовой папке. Не выдавать Build разрешение на `edit` в папке TIAGo. Если фактическая конфигурация не позволяет гарантировать read-only, использовать ручной разбор с подготовленным примером.

## Уровень 3 — кейс TIAGo, 80–120 минут

Задача: найти в документации TIAGo, где описаны окружение и запуск симуляции, затем подтвердить ответ.

| Время | Действие | Файлы/команды | Результат |
| --- | --- | --- | --- |
| 80–86 | Бриф | Открыть README TIAGo и `AGENTS.md` этого репозитория. | Понимают, что робот — отдельная среда Humble. |
| 86–95 | Запрос агенту | Просить назвать базовый ROS-дистрибутив и файл с запуском. | Ответ содержит конкретные пути. |
| 95–105 | Проверить руками | Открыть README и конфигурацию; проверить команду по тексту. | Подтверждено или отмечено расхождение. |
| 105–113 | Разобрать границу | Сопоставить root `AGENTS.md` и `3_Robot/TIAgo_humble/AGENTS.md`. | Понимают, что дочерние инструкции уточняют правила проекта робота. |
| 113–120 | Командный отчёт | Факт → источник → что агент сделал/не делал. | Краткий проверяемый отчёт без изменения файлов. |

OpenCode можно запускать на хосте как инструмент анализа файлов; ROS 2-команды для симуляции выполняются только в контейнере Humble. Для этого урока их не нужно запускать.

## План Б

- Нет провайдера: преподаватель показывает заранее записанный prompt/ответ и выполняет сверку по тем же исходным файлам.
- Agent list отличается от учебного скриншота: обсуждать фактически установленную версию, не требовать фиксированный набор агентов.
- Нельзя доказать read-only: использовать тестовую папку либо показать процесс вручную.
- TIAGo недоступен: использовать README/AGENTS.md и демонстрировать ссылку на реальное содержимое.
