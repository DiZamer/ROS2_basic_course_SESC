## Зачем это нужно в робототехнике

У проекта робота есть как минимум две истории, которые легко спутать:

- **где работает код:** ОС, ROS 2, библиотеки и инструменты сборки;
- **какой код и конфигурация изменялись:** исходники, параметры запуска, описание робота.

Dev Container задаёт общую рабочую среду. Git хранит выбранные версии файлов и позволяет увидеть историю изменений. Совместно они уменьшают расхождения между компьютерами, но не гарантируют полную идентичность: для этого также нужно фиксировать версии образов и зависимостей.

## Простые аналогии

- **Image** — чертёж мастерской, по которому её можно запустить.
- **Container** — запущенная мастерская с инструментами.
- **Bind mount** — общая папка, видимая и хосту, и контейнеру.
- **Docker volume** — отдельное хранилище, жизненным циклом которого управляет Docker.
- **Git** — журнал экспериментов: `add` выбирает правки, `commit` фиксирует подготовленный снимок.
- **Ветка** — отдельная линия эксперимента, не меняющая `main`, пока её изменения не интегрированы.

Аналогии помогают начать, но не заменяют техническое различие. Например, контейнер использует ядро хостовой ОС и не является полноценной виртуальной машиной.

## Модель 1. Жизненный цикл контейнерной среды

```text
Dockerfile ──build──> Image ──run──> Container
                                      │
Host project ───────── bind mount ────┘
```

- **Dockerfile** описывает, как собрать образ.
- **Image** — подготовленный шаблон среды.
- **Container** — запущенный экземпляр образа.
- **Bind mount** подключает папку проекта хоста внутрь контейнера.
- Изменения в writable layer контейнера могут исчезнуть при удалении экземпляра. Исходники проекта нужно хранить в подключённой рабочей папке.
- Docker volume — отдельный вид управляемого хранилища; его не следует считать синонимом bind mount.

### Что переживает пересоздание?

| Где создан файл | Типичное поведение при удалении контейнера |
| --- | --- |
| В смонтированной папке проекта | Файл остаётся в папке проекта на хосте. |
| В writable layer контейнера | Файл может быть удалён вместе с контейнером. |
| В Docker volume | Данные хранятся отдельно от контейнера; жизненным циклом управляет Docker. |

## Модель 2. Открытие Dev Container

```text
Открыть проект
     ↓
Прочитать devcontainer.json
     ↓
Получить или собрать image
     ↓
Запустить container и подключить workspace
     ↓
Работать в терминале контейнера
```

- **Reopen in Container** подключает редактор к рабочей среде проекта.
- **Rebuild Container** повторно собирает/создаёт окружение, когда изменилось описание сборки, например Dockerfile.
- Правка обычного исходного файла сама по себе обычно не требует Rebuild.
- Lifecycle hooks могут выполнять подготовку при создании контейнера или при его старте. На занятии используется только необходимое различие: одноразовая подготовка и действия при старте.

## Модель 3. Жизненный цикл Git-изменения

```text
Рабочая копия ──git add──> Индекс ──git commit──> Коммит
    │                           │                    │
    └─ git diff                 └─ git diff --staged └─ git log
```

- **Рабочая копия** — файлы, которые редактирует студент.
- **Индекс (staging)** — подготовленные изменения для следующего коммита.
- **Коммит** — зафиксированный снимок файлов в истории.
- `git status` показывает, какие файлы новые, изменённые или уже подготовленные.
- `git diff` сравнивает рабочую копию с индексом.
- `git diff --staged` показывает, что попадёт в следующий коммит.

### Минимальный Git-цикл

```bash
git status --short
git diff
git add README.md
git diff --staged
git commit -m "Добавил идею мобильного робота"
git log --oneline -1
```

Сначала просматриваем изменения, затем добавляем выбранный файл в индекс, проверяем подготовленный снимок и фиксируем его.

## Модель 4. Ветки и обмен с remote

```text
main:             A ── B
                       └── C ── D  feature/sensor

локальные коммиты ── push ──> remote
локальная история <── pull ── remote
```

- `git switch -c feature/sensor` создаёт и включает новую локальную ветку.
- `git fetch` обновляет локальные сведения об удалённой истории.
- `git pull` получает изменения и интегрирует их в текущую ветку.
- `git push` отправляет локальные коммиты на remote.

На занятии достаточно понимать назначение этих действий. Работа с реальным GitHub remote не обязательна для локальной практики.

## `.gitignore` и безопасная история

```gitignore
build/
install/
log/
__pycache__/
*.py[cod]
.env
*.pem
*.key
id_ed25519
```

- `build/`, `install/`, `log/` обычно создаются сборкой и могут быть созданы повторно.
- `.gitignore` помогает не добавлять такие новые неотслеживаемые файлы.
- `.gitignore` не прекращает отслеживание файла, уже добавленного в Git.
- Если секрет отправлен в remote, сначала отозвать или заменить секрет. Одно удаление файла из последнего коммита не отменяет утечку.

## Типичные ошибки

| Ошибка | Почему возникает | Что проверить |
| --- | --- | --- |
| Изменение исчезло | Файл создали вне смонтированной папки проекта | `pwd`, расположение workspace. |
| Контейнер не учитывает новый Dockerfile | Среда не пересобрана | Rebuild Container. |
| Коммит пустой | Файл не добавлен в индекс | `git status`, `git diff --staged`. |
| `build/` показывается в `git status` | Нет правила ignore или каталог уже отслеживается | `.gitignore`, `git check-ignore -v`. |
| `docker ps` не работает в контейнере | Docker CLI/доступ к daemon не настроены внутри | Выполнить Docker-команду в host terminal. |
| Ключ попал в Git | Секрет добавили до настройки ignore | Отозвать и заменить ключ; затем отдельно решать вопрос истории. |
