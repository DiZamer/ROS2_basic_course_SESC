## Цель и проверяемые результаты

К концу занятия студент объясняет разницу image/container/bind mount/volume; выполняет базовый Git-цикл с проверкой индекса; находит, где задаются и как запускаются среды уровня 2 и 3; может безопасно классифицировать изменение как код, результат сборки или секрет.

**Артефакты уровня 2:** чистый репозиторий с README и `.gitignore`, коммиты и ветка `feature/sensor`.

**Артефакт уровня 3:** аннотированная схема файлов контейнера TIAGo и запусковых хуков (без изменения проекта).

## Подготовка преподавателя

## Уровень 1 — лекция, 0–40 минут

### 0–4 — диагностический вход: «одна команда, два разных компьютера»

- **Показать:** два списка версий ОС/ROS-инструментов или иллюстрацию разных рабочих столов.
- **Спросить:** «Если у обоих одинаковый Git-коммит, гарантированно ли одинаково соберётся ROS-пакет?»
- **Объяснить:** нет; исходники одинаковы, но зависимости и окружение могут различаться.
- **Зафиксировать:** контейнер решает проблему среды частично, Git — проблему истории файлов.

### 4–11 — образ, контейнер и граница хост/контейнер

- Нарисовать Dockerfile → image → запущенный container.
- Уточнить: контейнер — изолированный процесс/окружение, но не отдельное ядро полноценной виртуальной машины.
- Выполнить `docker run --rm -it ubuntu:24.04 bash` на хосте; внутри показать `cat /etc/os-release`; затем `exit`.
- **Вопрос:** «Что было удалено при `exit`, а что осталось в образе?»
- **Переход:** «Процесс временный. Где же хранить код, который должен пережить его?»

### 11–17 — рабочая папка, bind mount и volume

- Показать схему общего каталога хоста и контейнера через bind mount.
- Отличить управляемый Docker volume от bind mount; объяснить, что слово «том» не обозначает автоматически папку проекта.
- Привязать к Dev Container: workspace студента монтируется как рабочая область; надо сохранять файлы внутри неё.
- **Формирующий вопрос:** «Если создать `test.txt` в `/tmp` контейнера, можно ли рассчитывать, что он останется после удаления контейнера?»

### 17–24 — Dev Container как контракт среды

- Разобрать небольшой пример: имя, источник образа или Dockerfile, `remoteUser`, рабочая папка.
- Представить последовательность: открыть проект → построить/получить образ → запустить контейнер → подключить редактор → выполнить команды в контейнере.
- Развести **Reopen** (вернуться к существующей среде) и **Rebuild** (собрать/запустить заново с новой конфигурацией).
- Сказать, что конфигурация сама по себе не фиксирует все версии внешних пакетов, если они не закреплены.

### 24–33 — Git: рабочая копия, индекс, коммит

- На одной строке показать три состояния: working tree → index → commit/HEAD.
- Выполнить концептуальный цикл: `git status --short` → `git add README.md` → `git diff --staged` → `git commit` → `git log --oneline`.
- Показать различие `git diff` и `git diff --staged`.
- Объяснить: коммит фиксирует именно индекс; `git add` выбирает содержимое следующего снимка.
- **Мини-проверка:** студент показывает пальцем, какие изменения попадут в следующий commit.

### 33–37 — ветки, remote и `.gitignore`

- Ветка — имя на истории, удобная линия отдельной работы.
- `fetch` обновляет сведения о remote; `pull` получает изменения и интегрирует их; `push` передаёт локальные коммиты.
- `.gitignore` помогает не добавлять сгенерированные и локальные файлы, но не «удаляет из истории» ранее добавленное.
- При утечке ключа — сначала отозвать/заменить его; одной правки Git недостаточно.

### 37–40 — резюме и выходной вопрос

- Студенты отвечают: «Код исчез после пересборки: что проверю? В `git status` лишний `build/`: что проверю? Секрет уже отправлен: что сделаю первым?»
- Заключительная фраза: «Контейнер отвечает за место выполнения, Git — за осмысленные снимки изменений».

## Уровень 2 — практика, 40–80 минут

Источник задания: [`../2_practice/02_container_git.md`](../2_practice/02_container_git.md). Практику проводить в общем контейнере уровня 2. Команды Docker запускать только в терминале, который имеет доступ к Docker daemon (обычно терминал хоста).

| Время | Задание | Что сделать | Контрольная точка |
| --- | --- | --- | --- |
| 40–45 | Убедиться в контексте | `hostname`, `whoami`, `pwd`, `ros2 --help` | Студент понимает, какой shell находится внутри контейнера. |
| 45–50 | Проверить контейнер с хоста | В host terminal: `docker ps`; найти Dev Container, при возможности `docker inspect` | Студент отличает host-side Docker от shell внутри контейнера. |
| 50–60 | Создать репозиторий | `git init -b main`, локальные имя/email, README, `status`, `add`, `diff --staged`, `commit` | Первый коммит виден через `git log --oneline`. |
| 60–67 | Исключить артефакты | Создать `build/`, `install/`, `log/`, затем добавить правила `.gitignore` | `git status --short` не показывает неотслеживаемый build-каталог. |
| 67–74 | Создать ветку и исследовать снимки | `git switch -c feature/sensor`, изменить README, `diff`, `add`, `commit`, вернуться в `main` | Коммит feature не принадлежит `main`, пока не выполнено слияние. |
| 74–80 | Проверка и мини-объяснение | Очистить незакоммиченную тестовую правку только после просмотра `git diff`; ответить на вопросы | Чистый working tree, корректные ветки, объяснение staged vs committed. |

**Команды из практики:** использовать готовые команды [`02_container_git.md`](../2_practice/02_container_git.md); перед `git restore` преподаватель требует посмотреть `git status` и `git diff`, поскольку restore удаляет незакоммиченную правку.

## Уровень 3 — архитектурный кейс TIAGo, 80–120 минут

**Безопасный режим:** чтение конфигурации и наблюдение за уже запущенным контейнером. Не останавливать узлы, не чистить `src/`, не запускать переимпорт и не триггерить полную сборку без предварительного времени/согласия группы.

### 80–86 — задача наблюдения

- Поставить вопрос: «Почему для TIAGo отдельное окружение, если для упражнений курса есть общий Dev Container?»
- Ожидаемые ответы: другой ROS-дистрибутив (Humble), собственные тяжёлые зависимости, отдельный workspace и графический сценарий.

### 86–98 — исследовать спецификацию контейнера

- Показать `3_Robot/TIAgo_humble/.devcontainer/devcontainer.json` и Dockerfile.
- На схеме отметить образ `osrf/ros:humble-desktop`, зависимости и пользовательские настройки.
- Сопоставить это с общим окружением уровня 2 (Jazzy/Ubuntu 24.04) без установки ROS на хост.

### 98–108 — прочитать lifecycle hooks и Git-границы

- Разобрать `post_create.sh` как одноразовую подготовку контейнера.
- Разобрать `post_start.sh` как действие при старте: импорт источников через `vcs`, зависимости, сборка workspace.
- Показать `ros2_ws/tiago.repos`: Git-репозиторий может описывать, откуда получить исходники, даже если сами внешние исходники не хранятся в родительском репозитории.
- Показать `.gitignore`: generated `build/`, `install/`, `log/` и внешние source trees следует интерпретировать по фактическим правилам проекта.

### 108–116 — наблюдение за работающей системой (только если уже поднята)

В отдельном терминале контейнера:

```bash
pwd
ros2 node list
```

- Сопоставить workspace и процессы ROS 2; ROS Graph подробно изучается позже.
- Ничего не завершать через `pkill`: остановка процессов не демонстрирует изоляцию контейнера и может нарушить демонстрацию.
- Если симуляция не запущена — перейти к анализу схемы, конфигов и ожидаемых шагов запуска из README.

### 116–120 — «архитектурная карточка» команды

Каждая пара за 60 секунд сообщает: (1) базовый образ/дистрибутив; (2) что монтируется как workspace; (3) какие действия автоматизированы; (4) какие файлы генерируются и почему они не равны исходникам.

## План Б и адаптация по времени

- **Docker не доступен:** схема образа/контейнера и готовая конфигурация; не тратить время на установку Docker на хосте.
- **Dev Container уровня 2 не подготовлен:** практика Git всё равно выполняется в доступном терминале; среду изучаем по проектному конфигу, установку ROS не начинаем.
- **TIAGo долго собирается/не стартует:** использовать README, конфиги и скрипты как архитектурный кейс.
- **Отставание до 5 минут:** сократить host Docker inspect, не сокращать различение `git diff`/`--staged` и правила секретов.
- **Есть резерв:** показать merge feature-ветки в `main` и разобрать несложный конфликт без push в общий репозиторий.

## Оценивание и вопросы

Устная проверка — 4 коротких сценария: «папка пропала», «build шумит в status», «нужно безопасно экспериментировать», «ключ уже запушен».

**Критерий успеха:** студент для каждого сценария выбирает проверяемый шаг и может объяснить его, а не только перечислить команды.
