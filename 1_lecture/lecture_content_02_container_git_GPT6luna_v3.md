> Авторская версия: занятие превращено в расследование инженерного инцидента **«Робот собрался в лаборатории, но не открылся дома»**. Образовательные результаты и тема Docker/Dev Container/Git сохранены; порядок объяснения и рамка занятия изменены.

## Завязка: инцидент в 09:05

Команда запускает учебного мобильного робота в аудитории. На компьютере преподавателя узлы собираются. Дома студент получает ошибку зависимости, один файл конфигурации «пропал», в remote случайно попал `build/`, а ключ доступа оказался в коммите.

Задача студентов — не искать одну волшебную кнопку, а построить карту причин:

- это сбой **среды** или **исходников**?
- файл был в рабочей папке контейнера или в его временном слое?
- изменение присутствует в рабочей копии, индексе, коммите или только на remote?
- нужно ли исправить `.gitignore`, собрать контейнер заново, интегрировать историю или отозвать секрет?

## Концепция занятия: «две книги учёта робота»

У команды есть две книги:

1. **Паспорт лаборатории** — чем окружение отличается от хоста, какой image строится, какие параметры запускаются, где доступна папка проекта.
2. **Журнал экспериментов** — какие изменения вошли в каждый коммит, в какой ветке они сделаны и что уже опубликовано.

Docker/Dev Container отвечает преимущественно за первую книгу. Git отвечает за вторую. Между ними нет автоматической магии: например, Dockerfile тоже является файлом Git-проекта и сам должен версионироваться.

## Результаты обучения

Студент сможет:

- объяснить, что Docker image и контейнер связаны как шаблон и экземпляр, но контейнер использует ядро host;
- точно назвать, является ли путь bind mount, Docker volume или файловым слоем контейнера;
- найти источник конфигурации Dev Container и выбрать reopen/rebuild по причине;
- восстановить путь файла через working tree → index → commit → remote;
- применять команды Git сначала для наблюдения состояния и только затем для изменения;
- настроить отдельный feature branch и понимать ограниченность `.gitignore`;
- правильно реагировать на опубликованный секрет;
- читать отдельное окружение робота TIAGo как пример многослойной инженерной системы.

## Расследование по уликам

### Улика A. «На двух ноутбуках разные ROS»

**Симптом:** одна версия пакета запускается у преподавателя, другая — нет.

**Разбор:** репозиторий отвечает за сохранение исходников, но не создаёт одинаковую ОС. Dockerfile и образ кодируют базовую среду. Контейнер — запущенный экземпляр; он изолирует процессы и filesystem view, но не является полноценной виртуальной машиной и разделяет ядро с хостом.

```text
Dockerfile ──build──> образ ──run──> контейнер с ROS-инструментами
                                           │
                                           └── ROS node / colcon / shell
```

**Техническая глубина:** контейнерный подход уменьшает расхождения, но одинаковый тег образа не всегда означает байтово закреплённый источник. Версии образов и зависимостей — следующий уровень дисциплины.

### Улика B. «Правка исчезла после перезапуска»

**Симптом:** `config.yaml` создали внутри контейнера, но после пересоздания его нет.

```text
Хостовая папка  <── bind mount ──>  /workspaces/project в контейнере
Docker volume   <── mount ────────>  отдельное управляемое хранилище
Writable layer  ──────────────────>  изменения слоя конкретного контейнера
```

**Вывод:** разместить проект в workspace mount. Bind mount отображает выбранную папку хоста; volume — отдельная область, которой управляет Docker; writable layer привязан к жизненному циклу экземпляра. Не называть все три «томом» без уточнения.

### Улика C. «Открыл проект, но инструменты не появились»

**Файл улика:** `devcontainer.json`.

Он описывает, как редактор запускает контейнер, подключает проект и настраивает рабочее место. Источник может быть готовым образом или локальным Dockerfile.

```text
Open/Reopen ──> подключиться к настроенному Dev Container
Rebuild      ──> пересобрать/пересоздать среду с обновлённой конфигурацией
```

Не всякое изменение требует rebuild; правка исходного Python-файла обычно не меняет image. Изменения Dockerfile обычно требуют пересборки. Точная политика определяется инструментом и конфигурацией.

### Улика D. «Коммит есть, но правки в нём нет»

```text
Рабочая копия ── git add ──> индекс ── git commit ──> история
   │ git diff                  │ git diff --staged
   └──────────── сравнить ─────┴───────────────────┘
```

Индекс — подготовленная версия файлов для следующего коммита. Значение `git status` читается как ответ на вопросы: что уже сохранено в HEAD, что staged, что изменено после staging и что ещё untracked?

**Реконструкция:**

```bash
git status --short
git diff
git add README.md
git diff --staged
git commit -m "Зафиксировал конфигурацию робота"
git log --oneline -3
```

### Улика E. «Нужно попробовать, не рискуя основной версией»

Ветка — линия работы, имя которой указывает на коммит. Новая ветка не дублирует весь проект как zip и не является remote.

```text
A──B──C  main
    └──D──E  feature/sensor
```

Ветка помогает изолировать разработку. После проверки изменения интегрируют слиянием. Remote хранит доступную удалённую копию/цель обмена. `fetch` обновляет информацию о remote; `pull` получает и интегрирует; `push` отправляет коммиты.

### Улика F. «В Git засорились артефакты и утёк ключ»

Пример правил `.gitignore`:

```gitignore
build/
install/
log/
__pycache__/
*.py[cod]
.env
*.pem
*.key
id_ed25519
```

`.gitignore` работает как правило отбора новых неотслеживаемых путей. Он не отменяет tracking существующего пути. Если secret был опубликован, его сначала отзывают и заменяют; очистка Git-истории сама по себе не отменяет утечку.

## Как связаны Docker и Git

```text
Git-репозиторий проекта
  ├─ исходники ROS 2
  ├─ Dockerfile / devcontainer.json     ← версионируются как обычные файлы
  ├─ launch/config/URDF                 ← версионируются, если нужны проекту
  └─ build/install/log                  ← обычно генерируются и игнорируются

Image/Container создают среду, Git сохраняет историю выбранных проектных файлов.
```

## Уровень 3 — расследование TIAGo

TIAGo — отдельный проектный контейнер ROS 2 Humble, не копия общего контейнера уровня 2. По [`../3_Robot/TIAgo_humble/README.md`](../3_Robot/TIAgo_humble/README.md): Dockerfile описывает образ; Dev Container подключает workspace; `post_create.sh` готовит базовое окружение; `post_start.sh` выполняет импорт внешних репозиториев, установку зависимостей и сборку. `ros2_ws/src/` создаётся из `tiago.repos` и содержит внешние проекты PAL, а не просто коммиты родительского курса.

**Задание:** на листе/слайде пометить, какой артефакт хранит Git-репозиторий курса, что появляется при импорте, что генерируется сборкой, и что студент не должен удалять в живой среде.

**Ограничение:** не убивать узлы, не вызывать `docker rm`, не чистить `src/`, `install/` и не запускать полный повторный импорт. Цель — инженерная диагностика, не повреждение симуляции.

## Типичные ошибочные выводы

- «Docker гарантирует 100% одинаковую сборку» → базу среды нужно фиксировать; внешние источники и hardware остаются факторами.
- «Все mounts — volumes» → различать bind mount, named volume и writable layer.
- «Всё, что видно в редакторе, уже закоммичено» → проверить `git status` и нужный diff.
- «Игнорирование удалило файл из Git» → `.gitignore` не снимает tracking.
- «Удалил ключ из коммита — проблема решена» → отозвать/заменить credential.
