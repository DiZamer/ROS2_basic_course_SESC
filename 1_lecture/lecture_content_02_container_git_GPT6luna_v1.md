## Центральная инженерная задача

На хостах студентов отличаются операционные системы и установленное ПО. ROS 2, Gazebo и связанные инструменты имеют взаимозависимые версии. Нужны два разных, дополняющих друг друга механизма:

- контейнер описывает **среду**, в которой запускаются инструменты;
- Git описывает **изменения проекта** и позволяет восстановить состояние его файлов.

Контейнер сам по себе не гарантирует идентичный результат сборки: на него влияют версии базового образа, пакетов и внешних источников. Для строгой повторяемости фиксируют версии образов и зависимостей. На этом занятии мы строим рабочую базу, а не систему supply-chain контроля.

## Новые термины и объяснения

| Термин | Объяснение для студента | Техническая граница |
| --- | --- | --- |
| Образ (image) | Сохранённый шаблон будущей мастерской. | Включает базовую файловую систему и инструкции/слои образа; сам по себе не является запущенным процессом. |
| Контейнер (container) | Запущенный экземпляр образа со своим процессом и изменяемым верхним слоем. | Контейнер использует ядро хостовой ОС и не равен полноценной виртуальной машине. Изоляция не абсолютна. |
| Bind mount | Общая папка: выбранный путь хоста виден по пути внутри контейнера. | Изменения файлов обычно видны по обе стороны; это не то же самое, что именованный volume. |
| Docker volume | Хранилище, жизненным циклом которого управляет Docker. | Подходит для постоянных данных контейнеров; не обязательно представляет папку проекта хоста. |
| Dev Container | Описанный конфигурацией контейнер, подключённый как рабочая среда разработки. | Конфигурация может строить image или ссылаться на готовый image; проектная папка обычно монтируется в контейнер. |
| Репозиторий Git | Проектные файлы вместе с базой истории версий. | Рабочая копия, индекс и коммиты — разные состояния, которые показывает `git status`. |
| Индекс (staging area) | Подготовленный список изменений для следующего коммита. | `git add` копирует выбранное состояние файла в индекс; последующие правки требуют повторного `git add`. |
| Коммит | Зафиксированный снимок проекта с автором, сообщением и родителем. | Коммит хранит дерево файлов и связь с историей, а не «архив всей папки компьютера». |
| Ветка | Подвижное имя, указывающее на коммит. | Создание ветки не копирует всю историю; ветви расходятся по мере появления коммитов. |
| Remote | Сохранённое имя удалённого репозитория и адреса обмена. | Remote-tracking refs обновляются через fetch; сами изменения не «появляются» в рабочей ветке до интеграции. |

## Учебный маршрут лекции — уровень 1

1. **Сбой воспроизводимости:** почему ROS 2 не следует устанавливать на хост курса и почему общий репозиторий не решает задачу среды.
2. **Слои контейнерной модели:** Dockerfile → image → container; где находятся код и изменения.
3. **Сохранение проекта:** bind mount vs volume vs изменяемый слой контейнера; что переживает удаление контейнера.
4. **Dev Container:** роль `devcontainer.json`, открытие проекта, rebuild после изменения сборочного описания и reopen при обычном возврате.
5. **Git как конечный автомат изменений:** untracked/modified → staged → committed; `status`, `diff`, `add`, `commit`, `log`, `restore`.
6. **Совместная работа:** ветка, remote, `fetch` (обновить сведения об удалённой истории), `pull` (получить и интегрировать), `push` (отправить локальные коммиты).
7. **Чистая история:** назначение `.gitignore`, артефакты `build/`, `install/`, `log/`, проверка staged-файлов и обращение с секретами.
8. **Мост к роботу:** сравнение лёгкой общей среды Jazzy и отдельного тяжёлого окружения TIAGo Humble.

## Схемы, которые должны сопровождать объяснение

### Контейнерная среда и данные проекта

```text
Dockerfile ──build──> image ──run──> container
                                  │
Host project ──bind mount─────────┘

Изменение в смонтированном проекте видно на хосте.
Изменение только в слое контейнера может исчезнуть при удалении контейнера.
Docker volume — отдельный тип хранилища, а не синоним bind mount.
```

Назначение: увидеть, что исполняемая среда и долговечность файлов — разные вопросы.

### Состояния Git

```text
Рабочая копия ──git add──> Индекс ──git commit──> История (HEAD)
     │                        ▲
     └──── git diff ──────────┘

Локальная история ──git push──> remote
Локальная история <──git pull── remote
```

Уточнение преподавателю: `git diff` по умолчанию показывает разницу рабочей копии и индекса; `git diff --staged` — индекса и последнего коммита.

## Минимальный набор команд

### Контейнер — демонстрация из терминала хоста

```bash
docker run --rm -it ubuntu:24.04 bash
```

Внутри контейнера:

```bash
cat /etc/os-release
exit
```

После выхода временный контейнер удалится из-за `--rm`. Для списка контейнеров и `docker exec` использовать терминал хоста, если Docker CLI/daemon не проброшены в Dev Container.

### Git — выполняется в учебной директории внутри общего контейнера

```bash
mkdir -p ~/my_robot && cd ~/my_robot
git init -b main
git config user.name "Student"
git config user.email "student@example.com"
printf '# My robot\n' > README.md
git status --short
git add README.md
git diff --staged
git commit -m "Добавил идею робота"
git log --oneline
```

`.gitignore` предотвращает обычное добавление совпадающих **неотслеживаемых** файлов, но не прекращает отслеживание уже добавленного файла. Если секрет уже отправлен в remote, его нужно считать скомпрометированным: отозвать/заменить секрет; удаление файла из последнего коммита не отзывает доступ и не стирает копии у других участников.

## Частые ошибки и диагностические вопросы

| Наблюдение | Вероятное объяснение | Проверка/действие |
| --- | --- | --- |
| Изменение в контейнере исчезло | Файл был создан вне workspace mount либо только в изменяемом слое контейнера | Сверить `pwd` с каталогом проекта; проверить bind mount в настройках Dev Container. |
| Окружение не изменилось после правки Dockerfile | Контейнер запущен из предыдущего образа | Выполнить Rebuild Container. |
| `git commit` сообщает, что нечего фиксировать | Индекс пуст или файл уже совпадает с коммитом | `git status`, затем `git add <файл>` и повторно проверить staged diff. |
| `build/` остаётся в `git status` | Папка уже отслеживается или правило игнорирования не совпадает | Проверить `git check-ignore -v <путь>`; `.gitignore` не отменяет отслеживание автоматически. |
| `docker ps` не работает из контейнера | Нет Docker CLI, доступа к сокету/daemon или прав | Использовать терминал хоста; не подключать Docker socket без необходимости. |
| Push содержит не ту ветку | Ошибка с текущей веткой или upstream | `git status -sb`, `git branch -vv`, затем выбрать корректный remote и ветку. |
