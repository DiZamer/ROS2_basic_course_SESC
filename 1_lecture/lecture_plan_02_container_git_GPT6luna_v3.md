# Занятие 2 — план GPT6luna v3: Расследование «робот не собрался дома»

> Свободная авторская версия на тему контейнеризации и Git. Три уровня курса сохранены; лекция организована как incident response без разрушительных действий. Содержание: [`lecture_content_02_container_git_GPT6luna_v3.md`](lecture_content_02_container_git_GPT6luna_v3.md). Слайды: [`../1_slides/GPT6luna/lecture_02_container_git_v3.md`](../1_slides/GPT6luna/lecture_02_container_git_v3.md).

## Режиссёрская идея

Студенты — инженерная группа, которой передали проект мобильного робота после сбоя. Каждая команда получает карточку с симптомом, формулирует гипотезу, выбирает **безопасную команду наблюдения**, читает результат и только потом предлагает исправление.

Две «книги учёта» занятия:

- **Паспорт лаборатории:** image/container/mount/devcontainer.
- **Журнал экспериментов:** working tree/index/commit/branch/remote.

## Учебные результаты

К финалу студент:

- объясняет роль контейнера и пределы его изоляции;
- различает bind mount, volume и writable layer;
- читает базовую карту Dev Container и отличает reopen от rebuild;
- интерпретирует `git status`, различает два вида `git diff`, делает коммит и ветку;
- понимает remote-синхронизацию и действие `.gitignore`;
- выбирает правильную реакцию на исчезнувший файл, старую конфигурацию, лишний build output и опубликованный ключ;
- связывает урок с домашним репозиторием собственной модели.

## Подготовка

- Уровень 2: открыть готовый Dev Container с ROS 2 Jazzy или иметь резервный терминал для локального Git-упражнения. ROS 2 на хосте не устанавливать.
- Уровень 3: приготовить открытые текстовые файлы `README.md`, `.devcontainer/devcontainer.json`, Dockerfile, `post_create.sh`, `post_start.sh`, `ros2_ws/tiago.repos` проекта TIAGo.
- На доске нарисовать две пустые книги учёта и шесть карточек улик.
- Подготовить feature tags из Marp-документа; слайды рассчитаны только на первые 40 минут.
- Не запускать новую полную сборку TIAGo: по проектному README она может занимать много времени.

## Расписание 40+40+40

| Время | Этап | Формат |
| --- | --- | --- |
| 0–40 | Уровень 1: брифинг и разбор улик | История + короткий разбор + контрольный вопрос. |
| 40–80 | Уровень 2: forensic-практика Git и среды | Пары, наблюдение состояний, безопасное исправление. |
| 80–120 | Уровень 3: TIAGo как готовая инженерная система | Исследование конфигурации без переписывания/удаления. |
| После | Домашнее задание | Применить инструменты к личной модели робота. |

## Уровень 1. Лекция через расследование, 0–40 минут

| Минуты | Сцена | Ход преподавателя | Ответ, к которому ведём |
| --- | --- | --- | --- |
| 0–3 | Вызов: сборка не прошла дома | Прочитать инцидент и показать ошибку зависимостей. Спросить, достаточно ли сравнить Git-коммиты. | Нет: надо сравнить и исходники, и среду. |
| 3–9 | Улика A: «разные ROS на двух машинах» | Построить Dockerfile → image → container; пояснить shared kernel и build/run. | Image описывает базовый шаблон, container выполняет процессы. |
| 9–14 | Улика B: «файл пропал» | Показать три области хранения: layer, bind mount, volume. Попросить выбрать, где хранить исходники. | Проект хранится в workspace mount; volume и bind mount — разные вещи. |
| 14–19 | Улика C: «инструмент не обновился» | Разобрать `devcontainer.json`, действие Reopen vs Rebuild. | Сначала определить, менялась ли конфигурация сборки или только исходники. |
| 19–27 | Улика D: «коммит пустой» | Живой переход untracked → staged → committed с `status`, `diff`, `diff --staged`. | Commit берет staged content, а не все файлы «сам собой». |
| 27–32 | Улика E: «эксперимент задел main» | Нарисовать ветвление; показать смысл local branch, remote-tracking ref. | Ветка изолирует линию изменений; remote — не синоним ветки. |
| 32–36 | Улика F: «build и ключ попали в историю» | Объяснить ignore и действия после утечки секрета. | Ignore для новых untracked файлов; утёкший ключ немедленно отзывать. |
| 36–40 | Собрать диагноз | Выдать 4 ситуации, попросить выбрать команду наблюдения до corrective action. | Наблюдение состояния предшествует потенциально разрушительной команде. |

### Реплики ведущего

- «Не лечим симптом, пока не знаем, в какой книге учёта он находится».
- «Контейнер — рабочее место процесса. Git — журнал выбранных изменений проекта».
- «Первый инженерный шаг — увидеть состояние: `pwd`, `docker ps`, `git status`, `git diff`».
- «Если ключ ушёл в remote, он больше не секрет — даже если коммит удалили».

### Вопросы по уликам

- Файл пропал после Rebuild: он был в mount или только в контейнерном слое?
- `README.md` изменён, а commit пуст: файл не staged или добавлена старая версия?
- Новый `build/` показывается в status: правило ignore отсутствует или каталог уже tracked?
- В `origin/main` новый commit, а в рабочей копии его не видно: обновляли ли remote-tracking ref и интегрировали ли его?

## Уровень 2. Практика «собери журнал изменений», 40–80 минут

Основной сценарий: [`../2_practice/02_container_git.md`](../2_practice/02_container_git.md). Пары получают роли **оператор** и **аудитор**; после каждого изменения аудитор просит сначала показать состояние.

| Время | Операция | Команда/действие | Вопрос аудитора |
| --- | --- | --- | --- |
| 40–45 | Подтвердить контекст | В Dev Container: `hostname`, `pwd`, `ros2 --help` | Это хост или среда курса? Как проверили? |
| 45–50 | Посмотреть контейнер снаружи | Host terminal: `docker ps` | Почему нельзя предполагать, что Docker CLI доступен внутри? |
| 50–59 | Завести репозиторий | `git init -b main`, `git status`, README, `git add`, `git diff --staged`, `git commit` | Что именно будет в следующем коммите? |
| 59–66 | Исключить шум | Создать `build/install/log`, добавить `.gitignore`, сравнить `status` | Как проверить, что файл действительно игнорируется? |
| 66–74 | Безопасная ветка эксперимента | `git switch -c feature/sensor`, изменить описание робота и коммитнуть | Что остаётся в `main` до merge? |
| 74–78 | Симуляция инцидента | Преподаватель выбирает баг-карточку; пара сначала диагностирует, затем меняет | Какая команда только наблюдает, а какая меняет/удаляет состояние? |
| 78–80 | Закрытие кейса | Exit ticket: назвать проблему, доказательство, действие | Проверка факта раньше исправления. |

В роли «инцидента» не публиковать настоящий ключ и не выполнять destructive push. Для секрета обсуждается только правильная реакция, без создания реального credential.

## Уровень 3. Кейс TIAGo «прочитай паспорт лаборатории», 80–120 минут

### Миссия групп

Подготовить краткое объяснение для студента, который впервые открыл [`../3_Robot/TIAgo_humble/README.md`](../3_Robot/TIAgo_humble/README.md): откуда берётся образ, когда создаётся workspace, как приходят пакеты TIAGo и что попадёт в Git.

| Время | Станция | Действие | Маркер готовности |
| --- | --- | --- | --- |
| 80–84 | Карточка проекта | Прочитать README: версии ROS/Ubuntu, назначение контейнера | Команда называет отличие от уровня 2. |
| 84–92 | Образ | Проследить Dockerfile и `devcontainer.json` | Участники находят build context и launch-настройки. |
| 92–100 | Автоматизация | Сравнить `post_create.sh` и `post_start.sh` | Однократная подготовка отличена от повторяемых/стартап-действий. |
| 100–107 | Происхождение кода | Прочитать `tiago.repos` и `.gitignore` | Ясно, что `vcs import` получает внешние источники, а colcon создаёт результаты сборки. |
| 107–114 | Система в работе | Если симуляция уже запущена: `ros2 node list`, `pwd`; иначе проследить README | Наблюдаем процессы, не вмешиваемся в них. |
| 114–120 | Брифинг следующей смены | Пара делает 1-минутную схему «config → container → sources → build → run» | Схема читаема и показывает источники/генерируемые данные. |

### Безопасные ограничения

- Не останавливать `robot_state_publisher` через `pkill`.
- Не удалять `ros2_ws/src`, `build`, `install` и не повторять импорт репозиториев.
- Не входить в Docker daemon из контейнера, если доступ не настроен.
- Все команды уровня 3 выполняются в контейнере Humble; команды host Docker — на хосте.

### План Б

Если TIAGo недоступен, stations работают на заранее открытых конфигурациях и схеме из `README.md`. Если нет общего Dev Container, уровень 2 проводит Git-цикл в заранее доступном терминале, а ROS-проверку заменяет демонстрация подготовленной среды. ROS на хост не устанавливать ради демонстрации.

## Разбор ошибок по модели «улика → гипотеза → проверка → действие»

| Улика | Гипотеза | Безопасная проверка | Следующее действие |
| --- | --- | --- | --- |
| Файл исчез | Файл вне workspace mount | `pwd`, проверить расположение workspace | Переместить/создать его в проекте и зафиксировать в Git. |
| Конфигурация старая | Образ/контейнер не пересоздан после build config change | Сравнить Dockerfile/devcontainer config и текущую среду | Rebuild Container. |
| Коммит пуст | Файл не в индексе | `git status`, `git diff`, `git diff --staged` | Выбрать нужные файлы через `git add`. |
| В status лишний build | Ignore отсутствует либо файлы уже tracked | `git check-ignore -v`, `git ls-files build` | Добавить правило или отдельно корректно прекратить tracking. |
| Remote отказал в push | Истории разошлись/нет прав/upstream | `git status -sb`, `git remote -v` | Fetch, осмотреть diff истории, интегрировать по инструкции команды. |
| Ключ опубликован | Secret exposure | Считать скомпрометированным | Отозвать и выпустить новый; затем координировать очистку истории при необходимости. |
