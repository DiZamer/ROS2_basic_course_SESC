# Занятие 2 — план GPT6luna v2: Контейнеризация и Git

> Расширенный инженерно-визуальный вариант. Каждый блок связывает наблюдаемый сбой, модель состояний и конкретную проверку. Содержание: [`lecture_content_02_container_git_GPT6luna_v2.md`](lecture_content_02_container_git_GPT6luna_v2.md). Слайды: [`../1_slides/GPT6luna/lecture_02_container_git_v2.md`](../1_slides/GPT6luna/lecture_02_container_git_v2.md).

## Цель занятия

Студент строит причинную модель reproducibility: конфигурация образа, запущенный контейнер, подключённые файлы, текущая версия проекта и удалённая история — отдельные части системы, которые надо проверять отдельно.

### Измеримые учебные результаты

К концу 120 минут студент без подсказки:

- объясняет разницу image/container/mount;
- рисует три состояния Git и показывает, какой diff нужен для каждого перехода;
- проходит локальный Git-цикл, включая branch и ignore;
- находит реальные конфигурационные файлы уровня 3 и объясняет lifecycle TIAGo;
- отвечает на четыре мини-кейса диагностики.

## Подготовка преподавателя

- Общий Dev Container уровня 2 готов к работе (Jazzy/Ubuntu 24.04); проверить ROS CLI и Git.
- Host terminal имеет доступ к Docker daemon для `docker ps`; никаких команд с root или Docker socket из контейнера не требуется.
- Открыты страницы/файлы: Docker image/container/mount docs, Pro Git, `3_Robot/TIAgo_humble/README.md`, `.devcontainer/devcontainer.json`, Dockerfile, hook scripts, `ros2_ws/tiago.repos`, `.gitignore`.
- Не начинать сборку TIAGo: первый полный запуск может импортировать большие зависимости и выполнить длительный build.
- Подготовить доску/слайд с тремя «слоями воспроизводимости»: environment / source / history.

## Уровень 1. Лекция, 0–40 минут

| Минуты | Блок | Учебная цель и объяснение | Визуальный/проверочный ход |
| --- | --- | --- | --- |
| 0–4 | Сбой «один commit, разные сборки» | Отделить одинаковость исходников от одинаковости среды. | Голосование: «Git clone гарантирует одинаковый результат сборки — да/нет?» |
| 4–10 | Environment stack | Dockerfile → image → container; build-time vs runtime. Контейнер делит ядро с host, в отличие от отдельной VM. | Слои-плашки; студенты дают по одному примеру содержимого image и процесса container. |
| 10–16 | Persistence | Writable layer, bind mount, volume; путь исходников отдельно от lifecycle контейнера. | Диаграмма удаления контейнера: что пропадает, что остаётся. |
| 16–22 | Dev Container | Конфигурация собирает/запускает среду и подключает workspace; Reopen и Rebuild — разные операции. Hooks происходят в заданных жизненных циклах. | Пошаговый flow открытия проекта; вопрос «изменили Dockerfile — что повторить?». |
| 22–29 | Git state machine | Working tree/index/HEAD; add формирует содержимое commit; status и два варианта diff. | На примере одной строки различить unstaged → staged → committed. |
| 29–34 | Ветки и синхронизация | Branch = указатель в локальной истории; remote = место обмена; fetch/pull/push имеют разные эффекты. | Схема divergence двух веток; откуда берётся `origin/main`. |
| 34–37 | Hygiene и секреты | Ignore не меняет уже отслеживаемое; generated outputs отличаются от исходников; утёкший secret надо отозвать. | Карточки «коммитить / игнорировать / отзывать». |
| 37–40 | Проверка понимания | Применить модель к четырём реальным симптомам. | Ticket quiz: потерян файл, build шумит, push rejected, ключ опубликован. |

### Ключевые фразы лектора

- «Одинаковый исходный код — важное условие, но это ещё не описание всей среды сборки».
- «Bind mount и volume решают похожую задачу хранения разными механизмами».
- «Коммит фиксирует подготовленный индекс; сначала проверяем, что именно подготовили».
- «`.gitignore` — фильтр при поиске новых файлов, а не ластик истории».
- «Утёкший секрет сначала отзывают. Историю можно переписать, но опубликованные копии уже могли разойтись».

### Демонстрационный Git-сценарий

Лектор показывает состояние до и после каждой команды. Команды выполняются в отдельном временном учебном репозитории:

```bash
git status --short
git diff
git add README.md
git diff --staged
git commit -m "Добавил идею робота"
git status --short
git log --oneline -1
```

Не выполнять показ на рабочем checkout курса.

## Уровень 2. Практика, 40–80 минут

Основное пошаговое задание — [`../2_practice/02_container_git.md`](../2_practice/02_container_git.md). Оно готовит локальный `~/git_practice`; преподаватель может добавить два контрольных упражнения ниже.

| Время | Действие студентов | Инструкция преподавателя | Критерий |
| --- | --- | --- | --- |
| 40–45 | Контекст среды: `hostname`, `whoami`, `pwd`, `ros2 --help` | Попросить сравнить текущую директорию и расположение исходников. | Студент знает, что выполняет команды внутри Dev Container. |
| 45–50 | Посмотреть список Docker-контейнеров из host terminal | Наблюдать связь VS Code ↔ container, не требовать Docker CLI внутри контейнера. | Найден контейнер среды или зафиксировано ограничение доступа к daemon. |
| 50–60 | Создать Git-репозиторий и первый commit | Попросить до commit прочесть `git status --short` и `git diff --staged`. | Первый коммит содержит README, не пустой и не захватывает случайные файлы. |
| 60–66 | Создать артефакт `build/`, добавить `.gitignore` | До и после правила сравнить `git status`. Затем пояснить случай уже tracked файла. | Студент знает предел действия ignore. |
| 66–74 | Создать `feature/sensor`, сделать коммит, переключиться на main | До каждого переключения сохранить/проверить рабочее состояние. | Изменение ветки не «теряется»; студент понимает раздельные вершины истории. |
| 74–78 | Диагностика карточек | Каждой паре дать один баг: «не попал файл», «пропал файл», «build в status», «не вижу remote commit». | Пара указывает команду наблюдения до команды изменения. |
| 78–80 | Exit ticket | Каждый студент записывает 1) команда проверки; 2) ожидаемое наблюдение. | Три ответа: `status`, корректный diff, безопасное действие. |

### Контрольные вопросы во время практики

1. Чем содержимое `git diff` отличается от `git diff --staged`?
2. Почему файл в `.gitignore` может всё ещё показываться как modified?
3. Где запускать `docker ps`, если у devcontainer не проброшен доступ к daemon?
4. Что изменится после `git switch main`, если feature-commit не слит?

## Уровень 3. Исследовательский кейс TIAGo, 80–120 минут

**Сценарий:** команда получает проект симуляционного TIAGo, который надо открыть на другом компьютере. Студенты выясняют, какая часть репозитория описывает среду, какая получает внешние ROS-пакеты и что сохраняется в Git.

| Время | Задача | Файлы / команды | Результат |
| --- | --- | --- | --- |
| 80–84 | Прочесть README и сформулировать, почему уровень 3 отделён | `3_Robot/TIAgo_humble/README.md` | ROS 2 Humble и тяжёлые зависимости отделены от учебного Jazzy. |
| 84–92 | Проследить описание образа и Dev Container | `.devcontainer/Dockerfile`, `devcontainer.json` | На схеме отмечены образ, параметры запуска и mount workspace. |
| 92–100 | Разобрать lifecycle | `post_create.sh`, `post_start.sh` | Различены однократная подготовка и шаги при запуске; объяснено, почему hooks могут быть длительными. |
| 100–107 | Проследить происхождение исходников | `ros2_ws/tiago.repos`, `.gitignore` | Понято, что исходники 18 внешних репозиториев импортируются, а не хранятся как обычные файлы проекта. |
| 107–114 | Наблюдать работающую среду или разобрать план Б | В контейнере: `pwd`, `ros2 node list` (только если система уже поднята) | Сопоставлена среда выполнения и ROS-процессы без их остановки. |
| 114–120 | Представить architecture card | 4 поля: image/runtime, workspace mount, dependency source, generated files | Команда умеет объяснить воспроизводимость своего кейса. |

### Смелость без поломки

Для этого занятия смелый тест — намеренно проследить **пропажу/сохранение файла мысленно по слоям**, а не удалять живой контейнер или убивать узлы. Если преподаватель заранее подготовил безопасный disposable container, допускается показать разницу между writable layer и bind mount на пустом файле; исходный Dev Container курса и проект TIAGo не использовать для эксперимента на удаление.

### Если TIAGo не запущен

План Б полноценный: схема Dockerfile → image → container; чтение `devcontainer.json`; последовательность hooks; `tiago.repos`; правила `.gitignore`; рисунок workspace `src/build/install/log`. Кейс остаётся архитектурным и не требует живого ROS Graph.

## Итоговая оценка

Exit ticket оценивается по 4 признакам:

- различена среда и исходники;
- различены рабочая копия и staged snapshot;
- предложена проверка перед разрушительным действием;
- при утечке названо немедленное отзыв/ротация credential.
