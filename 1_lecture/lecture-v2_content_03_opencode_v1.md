# Содержание занятия 3 · lecture-v2

> Тема: агентная инженерия с OpenCode. Лекция объясняет ИИ-агента простыми словами, затем показывает рабочую модель «запрос → контекст → инструменты → проверка результата».

## Результаты обучения

Студент:

1. объясняет, чем ИИ-агент отличается от обычного поиска и автодополнения;
2. составляет запрос с целью, контекстом, ограничениями и проверяемым результатом;
3. находит инструкции проекта в `AGENTS.md` и настройки в `opencode.jsonc`;
4. объясняет назначение `allow`, `ask`, `deny` и проверяет эффективные права до запуска инструментов;
5. использует режим Plan для исследования, не полагаясь только на название режима как на гарантию безопасности;
6. сверяет ответ агента с файлами проекта и надёжными источниками;
7. знает, что модель может ошибаться и не должна получать секреты.

## Что это и зачем

ИИ-агент для программирования принимает запрос, читает доступный контекст и может использовать инструменты: искать файлы, открывать документы, выполнять команды, предлагать или вносить правки. OpenCode — один из таких инструментов.

Для ROS 2 проекта агент может объяснить назначение пакета TIAGo или найти launch-файл. Он не знает автоматически, какой файл является источником истины, и способен уверенно ошибиться. Поэтому инженер задаёт задачу, границы и проверку результата.

## Аналогия и её границы

**Аналогия:** агент — стажёр, который быстро читает папки и выполняет поручения.

**Граница аналогии:** агент — программа, а не человек. Его «понимание» основано на модели и доступных данных; ответ может быть правдоподобным, но неверным. Инструкции и права снижают риск, но не гарантируют правильность результата.

## Модель работы агента

```text
Запрос студента
      ↓
Контекст: открытая папка + AGENTS.md + найденные файлы
      ↓
Модель предлагает следующий шаг
      ↓
Проверка прав инструмента: allow / ask / deny
      ↓
Инструмент читает, ищет, запускает или редактирует
      ↓
Результат проверяет студент
```

- **Prompt / запрос** задаёт задачу.
- **Контекст** — доступные агенту инструкции и материалы проекта.
- **Инструмент** — операция, например чтение файла или shell-команда.
- **Permission** — правило, разрешающее операцию автоматически, требующее подтверждения или запрещающее её.
- Эффективное право зависит от агента, версии OpenCode, пользовательской и проектной конфигурации. Проверяй настройки; не выводи право только из названия Plan/Build.

## Как написать полезный запрос

```text
Цель: объяснить пакет tiago_description.
Контекст: используй только файлы в 3_Robot/TIAgo_humble.
Ограничение: ничего не изменяй и не запускай.
Формат: 3 пункта + пути к подтверждающим файлам.
Проверка: укажи, какие файлы ты прочитал.
```

Запрос становится лучше, когда результат можно проверить по конкретным файлам, командам или наблюдаемому поведению.

## Инструкции и права

### `AGENTS.md`

Инструкции проекта описывают его цели, структуру, стиль и ограничения. OpenCode использует обнаруженные правила как контекст при работе. Инструкции помогают держать общий курс, но сами по себе не ограничивают shell-доступ как техническая песочница.

### `opencode.jsonc` и permission

В конфигурации можно задавать доступ к инструментам. Общие значения:

| Право | Смысл |
| --- | --- |
| `allow` | инструмент можно запускать без отдельного подтверждения; |
| `ask` | пользователь решает перед действием; |
| `deny` | действие запрещено конфигурацией. |

Для инструментов изменения особенно важно проверить `edit` и `bash`. Настройки могут задаваться на разных уровнях и объединяться. Перед практикой открой фактический `opencode.jsonc` и проверь, какой агент и какие права будут применены.

### Plan и Build

- **Plan** предназначен для анализа и планирования; по умолчанию он ограничивает изменения.
- **Build** — агент для выполнения задач; доступ к редактированию и shell зависит от его прав.
- Конфигурация пользователя или проекта может менять эффективные разрешения. Поэтому упражнение выполняется в безопасной тестовой папке и не разрешает действия, меняющие TIAGo.
- **Subagent** — вспомогательный агент для отдельной задачи. Например, Explore специализируется на исследовании проекта; реальные разрешения нужно сверять в текущей конфигурации.

## Минимальный рабочий цикл

```text
1. Сформулировать конкретный вопрос.
2. Ограничить файлы и действия.
3. Выбрать агента и проверить его права.
4. Попросить ссылки/пути, которыми подтверждается ответ.
5. Сверить вывод с исходными файлами или официальной документацией.
6. Только затем решать, применять ли предложенные изменения.
```

## Три уровня занятия

### Уровень 1 — лекция

Показать модель агента и разбор хорошего/плохого запроса. Демонстрацию выполнять только на безопасном вопросе чтения: найти README и пересказать назначение пары каталогов.

### Уровень 2 — практика

В отдельной тестовой папке студент запускает OpenCode, задаёт read-only вопрос о созданных учебных файлах, проверяет пути и убеждается, что файлы не изменились. Для чтения репозитория используются Plan или Explore только после просмотра фактических permissions.

### Уровень 3 — TIAGo

В `3_Robot/TIAgo_humble/` студент спрашивает о назначении одного пакета или конфигурационного файла, требует указать источник и сверяет ответ с README/деревом workspace. Не просить Build исправлять код робота и не давать ему команду запуска симуляции.

### Домашняя работа

Студент задаёт агенту вопрос о собственной `robot_idea.md`, проверяет утверждения и записывает в дневник один подтверждённый вывод и одну границу/неопределённость.

## Безопасная граница

- Не отправлять в запросы пароли, API-токены, приватные SSH-ключи, `.env` и данные, которые не должны покидать компьютер.
- Не просить агента запускать команды управления реальным роботом.
- Перед потенциальным изменением — проверить diff и сделать резервную копию/коммит по правилам курса.
- Запрос «ничего не меняй» — полезная инструкция, но технические permissions всё равно следует проверить.

## Типичные ошибки

| Ошибка | Почему | Что сделать |
| --- | --- | --- |
| Слишком общий запрос | Агент угадывает контекст и может перечислить несуществующее | Ограничить папку, формат ответа и требование доказательств. |
| Доверие к правдоподобному выводу | Текст модели не равен проверенному факту | Открыть названные файлы и проверить цитаты/пути. |
| Считать Plan безусловно read-only | Конфигурации и версии различаются | Проверить эффективные permissions; практиковаться на копии/тестовой папке. |
| Вставить секрет в prompt | Текст может попасть в историю/провайдеру | Удалить секрет из запроса; работать с обезличенными примерами. |
| Разрешить Build менять TIAGo | Упражнение может повредить рабочий проект | Для занятия ограничиться чтением; изменения тестировать отдельно. |
