## Часть 1 (0-40 минут)

### 0-4 мин — Блок 1. Что такое ROS2 (Robot Operating System 2) и зачем он нужен роботу

**Схема на слайде**: Mermaid «Программы робота без middleware vs с ROS2».

**Что сказать**:
- ROS2 — это не библиотека и не операционная система. Это среда, в которой отдельные программы робота обмениваются сообщениями.
- Без ROS2 каждый раз пишем свой протокол, сериализацию, обнаружение узлов. С ROS2 — только бизнес-логику.
- ROS2 — как городская инфраструктура: дороги, почта, адреса, светофоры. Программы робота — жители, которые пользуются готовой инфраструктурой.
- Эта лекция — фундамент. Дальше сенсорика, YOLO (You Only Look Once), SLAM (Simultaneous Localization And Mapping), Nav2 (Navigation 2), манипуляторы. ROS2 — общий язык для всех этих тем.

**Демонстрация**: не нужна.

**Переход**: «Теперь посмотрим, как ROS2 устроен изнутри».

### 4-8 мин — Блок 2а. Node, ROS Graph (Robot Operating System Graph), Executor и callbacks

**Схема на слайде**: Mermaid ROS Graph с 3-4 узлами (camera -> YOLO -> planner -> motor).

**Что сказать**:
- Node — отдельная программа робота, которая решает одну задачу.
- ROS Graph — сеть узлов и связей между ними. Как социальный граф, но для программ.
- Executor — диспетчер, который вызывает обработчики событий (callbacks) при получении сообщений или срабатывании таймеров.
- Аналогия: node — сотрудник в офисе, Executor — секретарь, раскладывающий входящие по папкам.

**Демонстрация**: не в этом блоке (первая демонстрация CLI (Command Line Interface) будет в блоке 3).

**Переход**: «Как сообщения физически доходят от одного узла к другому? Этим занимается middleware».

### 8-14 мин — Блок 2б. Middleware: DDS (Data Distribution Service), RMW (ROS Middleware), discovery

**Схема на слайде**: Mermaid «путь сообщения» — publisher → RMW → DDS → сеть → DDS → RMW → subscriber.

**Что сказать**:
- Middleware — слой между ROS2 API (ваш `publish()`) и реальной сетью. Вы не пишете сетевой код.
- DDS — протокол, который реально передает данные. Реализует QoS (Quality of Service), discovery, транспорт.
- RMW — тонкий адаптер между ROS2 API и конкретным DDS. Можно менять DDS без изменения кода узла.
- Discovery — автоматическое знакомство узлов. Запустили узел — все остальные узнали о нем.
- Робот делится на подсистемы: Mobile Base, Navigation, Manipulation, Perception, Safety, LLM (Large Language Model) Bridge, Simulation — каждая со своими интерфейсами.

**Демонстрация**: `ros2 doctor --report` — показать окружение.

**Переход**: «Хватит теории. Давайте запустим ROS2 и проверим, что все работает».

### 18-20 мин — Блок 5. Node, Executor и callbacks

**Что сказать**:
- Node — программа, которая делает одну задачу и общается с другими узлами.
- `spin()` — запускает цикл обработки событий. Если забыть `spin()`, колбэки не вызываются.

**Код на слайде** — минимальный узел (5-7 строк):
```python
import rclpy
from rclpy.node import Node

class MyNode(Node):
    def __init__(self):
        super().__init__('my_node')
        self.create_timer(1.0, self.callback)

    def callback(self):
        self.get_logger().info('Tick')

rclpy.init()
rclpy.spin(MyNode())
```

**CLI-демонстрация**: `ros2 node list`, `ros2 node info /my_node`, `rqt_graph`.

**Ожидаемый результат**: узел виден в `ros2 node list`, `rqt_graph` показывает один узел.

**Переход**: «Узел есть. Теперь свяжем два узла через topic».

### 20-28 мин — Блок 6. Topic, publisher, subscriber и message types

**Схема на слайде**: publisher → `/chatter` (std_msgs/String) → subscriber.

**Что сказать**:
- Topic — именованный канал. Publisher отправляет сообщения, subscriber читает.
- Аналогия: Telegram-канал. Один пишет, многие читают.
- В роботе: `/cmd_vel` — команда скорости, `/scan` — данные лидара, `/camera/image_raw` — видеопоток.

**Код на слайде** — publisher (8 строк):
```python
self.pub = self.create_publisher(String, '/chatter', 10)
msg = String()
msg.data = f'Count: {self.count}'
self.pub.publish(msg)
```

**Код на слайде** — subscriber (5 строк):
```python
self.sub = self.create_subscription(String, '/chatter', self.callback, 10)

def callback(self, msg):
    self.get_logger().info(f'I heard: {msg.data}')
```

**CLI-демонстрация**:
```bash
# Терминал 1: запуск publisher
# Терминал 2:
ros2 topic list
ros2 topic echo /chatter
ros2 topic hz /chatter
ros2 topic info /chatter
ros2 topic pub /chatter std_msgs/String "data: 'Hello from CLI'"
```

**Ожидаемый результат**: `ros2 topic echo` показывает поток сообщений; `ros2 topic pub` вставляет сообщение с клавиатуры.

**Типичные ошибки**: разные message types у pub и sub — соединения не будет.

**Переход**: «Topic — поток. А если нужен запрос-ответ? Для этого — service».

### 28-33 мин — Блок 7. Service и client

**Схема на слайде**: client → request → service server → response, в формате sequenceDiagram.

**Что сказать**:
- Service — короткий запрос и ответ. В отличие от topic — связь точка-точка, с ожиданием ответа.
- Когда нужно: запросить статус батареи, активировать emergency stop, получить конфигурацию.
- Аналогия: звонок в справочную — задал вопрос, получил ответ.

**Код на слайде** — service server (10 строк): принимает два числа, возвращает сумму.

**Код на слайде** — client (5 строк): отправляет запрос, ждет ответ.

**CLI-демонстрация**:
```bash
ros2 service list
ros2 service type /add_two_ints
ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 5, b: 3}"
```

**Ожидаемый результат**: CLI возвращает `sum: 8`.

**Переход**: «Service — быстро. А если задача длится секунды или минуты? Action».

### 33-38 мин — Блок 8. Action server и action client

**Схема на слайде**: goal → action server → feedback (прогресс) → result, с возможностью cancel.

**Что сказать**:
- Action — длительная задача с прогрессом и возможностью отмены.
- Четыре элемента: goal (цель), feedback (прогресс), result (итог), cancel (отмена).
- Аналогия: доставка пиццы — заказ (goal), «выехал, подъезжаю» (feedback), «доставлено» (result), можно отменить.
- В роботе: `/navigate_to_pose` — ехать к точке с отчетом о расстоянии.

**Код на слайде** — фрагмент action server с feedback (10 строк).

**CLI-демонстрация**:
```bash
ros2 action list
ros2 action send_goal /fibonacci example_interfaces/action/Fibonacci "{order: 5}" --feedback
```

**Ожидаемый результат**: CLI показывает feedback (частичные последовательности) и финальный result.

### 38-40 мин — Вопросы, фиксация и переход

**Что сказать**:
- Сравнение topic / service / action:
  - **Topic**: поток, много получателей, нет ответа — `/scan`, `/cmd_vel`
  - **Service**: запрос-ответ, точка-точка — `/emergency_stop`, диагностика
  - **Action**: длительная задача, прогресс, отмена — `/navigate_to_pose`
- Вопрос: «Что выберете для команды двигателю? Для статуса батареи? Для навигации к точке?»

**Переход**: «Мы научились запускать отдельные узлы. Во второй части — как запускать систему целиком, как связать координаты робота и как ROS2 работает в реальных проектах».

### 40-46 мин — Блок 9. Parameters и launch

**Схема на слайде**: launch-файл → запускает несколько узлов, каждому — YAML с параметрами.

**Что сказать**:
- Parameter — настройка узла, которая меняется без перекомпиляции.
- Launch — сценарий запуска нескольких узлов одной командой.
- Аналогия parameters: настройки телефона (яркость, громкость). Меняются без перепрошивки.
- Аналогия launch: сценарий театральной постановки — свет, звук, актеры выходят по плану, а не вручную.

**Код на слайде**: узел с параметром `publish_rate` (5 строк), YAML-конфиг (3 строки), launch.py (10 строк).

**CLI-демонстрация**:
```bash

# В другом терминале:
ros2 param list
ros2 param set /my_node publish_rate 5.0
```

**Ожидаемый результат**: launch запускает два узла; `ros2 param set` меняет поведение на лету.

**Типичные ошибки**: параметр не объявлен — не виден в `ros2 param list`; путь к YAML неверный.

### 46-52 мин — Блок 10. tf2 и дерево координат

**Схема на слайде**: дерево `map → odom → base_link → lidar_link / camera_link / arm_*`.

**Что сказать**:
- tf2 — карта систем координат робота. Каждый датчик, колесо, звено руки имеет свой frame.
- LiDAR видит препятствие в `lidar_link`, а моторы едут в `base_link`. tf2 пересчитывает между ними.
- Аналогия: GPS + поэтажный план здания — вы знаете, где находитесь относительно комнаты, этажа, улицы.

**CLI-демонстрация**:
```bash
ros2 run tf2_ros tf2_echo world robot_base
ros2 run tf2_tools view_frames
```

**Ожидаемый результат**: `view_frames` генерирует PDF с деревом; `tf2_echo` показывает координаты в реальном времени.

**Типичные ошибки**: разное время (timestamp) у transform-ов; неправильное имя frame — transform не публикуется.

**Переход**: «tf2 связывает координаты. Теперь — как гарантировать, что сообщения доходят? QoS».

### 52-56 мин — Блоки 11-12. QoS и Lifecycle

**Схема на слайде**: таблица QoS-политик и диаграмма состояний lifecycle node.

**Что сказать (QoS, 52-54 мин)**:
- QoS — правила доставки сообщений: надежно или быстро, хранить историю или нет.
- `/scan` — best effort (пропуск кадра не страшен). `/cmd_vel` — reliable (нельзя терять команду).
- Аналогия: выбор службы доставки — «срочно, могут потерять» vs «надежно, с подтверждением».

**Код на слайде**: QoS-профиль в коде (2 строки).

**Что сказать (Lifecycle, 54-56 мин)**:
- Lifecycle — модель состояний узла: unconfigured → inactive → active.
- Драйвер мотора должен сначала настроить порт, потом активировать контроль, потом принимать `/cmd_vel`.
- Аналогия: запуск автомобиля — ключ → стартер → прогрев → поехали.

**Демонстрация**: показать диаграмму состояний; CLI `ros2 lifecycle list / ros2 lifecycle set`.

**Переход**: «Теперь посмотрим, как все эти механизмы собираются в реальную систему робота».

### 67-72 мин — Блок 15. Архитектурный мост к MoveIt2

**Схема на слайде**: MoveIt2 pipeline — URDF + joint limits + planning scene → IK (Inverse Kinematics) → trajectory → ros2_control.

**Что сказать**:

- Рука не может просто «поехать в точку» — нужен план без столкновений.
- Основной интерфейс: `move_group` action server.
- Аналогия: диспетчер движения руки, который проверяет путь до команды приводам.

**Демонстрация (план А)**: запуск MoveIt2 с роботом, планирование движения схвата в rviz2.

**План Б**: схема MoveIt2 pipeline, структура конфигов, фрагмент кода Python API.

### 72-76 мин — Блок 16. Архитектурный мост к YOLO

**Схема на слайде**: camera → `/camera/image_raw` → yolo_node → `/detections` → safety_node / planner.

**Что сказать**:
- YOLO — модель компьютерного зрения. В ROS2 — узел, который подписан на `/camera/image_raw` и публикует найденные объекты в `/detections`.
- YOLO — это зрение, которое быстро говорит: «вижу объект здесь, с такой-то уверенностью».
- **Ключевое правило безопасности**: YOLO публикует факты и confidence. YOLO не управляет движением. Решение принимает safety/planner.

**Демонстрация (план А)**: YOLO-узел с камеры робота, `ros2 topic echo /detections`.

**План Б**: схема pipeline, фрагмент кода YOLO-узла, message type `Detection2DArray`.

**Код на слайде**: YOLO-узел — подписка на image, публикация detections (8-10 строк).

**Граница безопасности**: perception публикует факты. Control принимает решения. Никаких прямых связей.

**Переход**: «Робот видит. Теперь — как робот понимает человека? LLM bridge».

### 76-80 мин — Блок 17. Архитектурный мост к LLM bridge

**Схема на слайде**: голосовая команда → LLM → task planner → Behavior Tree → policy layer → safety layer → Nav2/MoveIt2.

**Что сказать**:
- LLM bridge переводит команду человека в разрешенные high-level actions робота.
- Пример: «принеси тапочки» → LLM формирует план: найти тапочки (YOLO), подъехать (Nav2), взять (MoveIt2), привезти (Nav2).
- **Ключевое правило безопасности**: LLM не управляет моторами, PWM, током, скоростью колес. LLM формирует только high-level request, который проходит через policy layer (что разрешено) и safety layer (безопасно ли сейчас).
- Аналогия: переводчик с человеческого языка на язык действий робота, но с жесткими правилами — перевести можно только разрешенные фразы.

**План Б**: схема pipeline с 5-7 шагами, фрагмент bridge-узла с фиксированным словарем команд, диаграмма safety/policy слоев.

**Граница безопасности**: LLM → high-level request → policy → safety → ROS2 action. Никакого прямого доступа к `/cmd_vel` или PWM.
