## Центральный вопрос

> Как другой студент может получить ту же среду и понять, какие изменения привели к результату?

Ответ состоит из двух описаний:

1. **Описание среды исполнения:** образ, параметры запуска, mounts, `devcontainer.json`, настройки зависимостей.
2. **Описание эволюции проекта:** изменения файлов, индекс, коммиты, ветки, удалённые копии.

Git не фиксирует автоматически Docker daemon, версию всех внешних пакетов, оборудование или сетевое окружение. Docker не версионирует исходники и не гарантирует идентичные результаты при незакреплённых тегах/зависимостях. Воспроизводимый робототехнический проект связывает обе стороны.

## Результаты обучения

После занятия студент способен:

- нарисовать путь `Dockerfile → image → container` и отдельно показать поток проекта через bind mount;
- обосновать, почему container — не VM и почему его удаляемый слой не является надёжным хранилищем исходников;
- отличить Docker volume от bind mount, назвать типичный сценарий каждого;
- прочитать базовые поля `devcontainer.json` и объяснить, когда нужен rebuild;
- объяснить Git working tree, index, `HEAD`, локальную ветку и remote-tracking branch на диаграмме состояний;
- диагностировать untracked/staged/modified файлы через `git status`, `git diff`, `git diff --staged`;
- объяснить разницу `fetch`, `pull`, `push` и роль upstream;
- защитить репозиторий от случайного добавления build-артефактов и не обещать, что `.gitignore` спасает ранее tracked файлы или уже опубликованные секреты;
- сопоставить эту модель с тем, как устроен отдельный Humble-контейнер TIAGo.

## Концептуальная карта и причинно-следственные связи

### 1. Почему важна воспроизводимость

Сборка пакета зависит не только от исходников. На неё влияют ОС/ABI, compiler/toolchain, ROS distribution, системные и Python-зависимости, конфигурация окружения, исходные версии пакетов, иногда GPU/драйверы и графические интерфейсы.

```text
Результат сборки = исходники
                 + версия ОС и ROS
                 + системные/языковые зависимости
                 + настройки сборки
                 + внешние репозитории/версии
```

Контейнер помогает задать эту базу в переносимом виде. Для более строгой повторяемости версии зависимостей и внешних репозиториев тоже следует фиксировать.

### 2. Образ и контейнер

| Сущность | Простая модель | Инженерное описание | На что не похожа |
| --- | --- | --- | --- |
| Dockerfile | Рецепт сборки мастерской | Декларативная последовательность инструкций для построения образа | Не контейнер и не список команд, исполняемых при каждом запуске контейнера |
| Image | Шаблон мастерской | Набор слоёв и метаданных, на основании которого создают контейнеры | Не процесс; теги вроде `latest` сами по себе не являются неизменяемым pin |
| Container | Работающая мастерская | Изолированное выполнение процесса с конфигурацией, mounts и writable layer | Не отдельная VM: используется ядро хоста; привилегии и mounts влияют на границу изоляции |

Изменения в контейнерном writable layer относятся к экземпляру контейнера. Удаление экземпляра уничтожает этот слой, если данные не вынесены в mount или не сохранены в image/внешнем хранилище.

### 3. Где живут файлы

| Способ хранения | Кто задаёт источник | Типичный сценарий | Судьба при удалении контейнера |
| --- | --- | --- | --- |
| Writable layer | Docker | Временные изменения файлов внутри работающего контейнера | Удаляется вместе с контейнером |
| Bind mount | Пользователь задаёт путь хоста и путь контейнера | Исходники проекта, редактируемые хостовым редактором | Данные остаются в исходном каталоге хоста |
| Docker volume | Docker управляет хранилищем | Постоянные данные или обмен данными контейнеров | Живёт отдельно от контейнера до удаления самого volume |

Данные сохраняются по-разному; «том» — не универсальное имя для любой смонтированной папки.

### 4. Dev Container как интерфейс разработчика

Dev Container связывает образ/способ сборки, mount рабочего проекта, пользователя, рабочую папку, дополнительные настройки редактора и lifecycle hooks. Он не «переносит ROS на хост»: ROS-процессы и инструменты работают в контейнерном окружении.

```text
devcontainer.json
  ├─ образ или Dockerfile ──> container runtime
  ├─ workspace mount ───────> исходники проекта
  ├─ настройки редактора ───> терминал / расширения / user
  └─ lifecycle hooks ───────> подготовка и запуск окружения
```

- **Reopen** — снова подключиться к существующему/уже созданному контейнеру.
- **Rebuild** — пересобрать конфигурацию образа/контейнера после соответствующих изменений.
- Точные lifecycle hooks, например `postCreateCommand` и `postStartCommand`, имеют разные моменты вызова; см. Dev Container Specification.
- Hooks не должны объясняться как полноценная система orchestration или как команда, которая обязана заново исполнять полный build при каждом открытии любого контейнера.

### 5. Git как модель состояний

```text
                 git add                     git commit
Рабочая копия ─────────────> Индекс ───────────────────> Коммит (HEAD)
      │                          │                             │
      └── git diff ──────────────┘                             └─ git log
                                 └── git diff --staged ─────────────┘
```

- **Working tree** — файлы, которые студент видит и редактирует.
- **Index/staging area** — проектируемое содержимое следующего коммита.
- **Commit** — зафиксированное дерево файлов с авторством, сообщением и родительской историей.
- `git status` сравнивает состояния HEAD, index и working tree, а также сообщает о новых неотслеживаемых файлах.
- `git add` добавляет текущую версию выбранного пути в index; следующую редакцию файла надо отдельно подготовить.

### 6. Ветки и remote — два разных измерения

Ветка — имя, которое сдвигается на новый коммит. Remote — конфигурация места обмена. `origin/main` обычно remote-tracking reference: локальная запись о состоянии ветки на remote, обновляемая fetch.

```text
                         B──C  feature/sensor
                        /     
A───D  main             
│
└─ origin/main (снимок, полученный последним fetch)
```

- `git fetch origin` получает объекты и обновляет remote-tracking refs, но не обязан менять текущую рабочую ветку.
- `git pull` получает изменения и интегрирует их в текущую ветку (конкретная стратегия зависит от конфигурации).
- `git push` публикует локальные коммиты в удалённую ветку, если настройки и права позволяют.
- Слияние может создать merge commit или применить другую стратегию; студентам этого занятия достаточно увидеть простое слияние и понять, что конфликт — не потеря истории.

### 7. `.gitignore`, артефакты и секреты

```gitignore
build/
install/
log/
__pycache__/
*.py[cod]
.env
*.pem
*.key
id_ed25519
```

- ROS/colcon-сборка создаёт каталоги, которые генерируются повторно; обычно в Git хранят исходники и необходимые описания, а не build/install/log.
- `.gitignore` действует для неотслеживаемых путей; файл, уже tracked, останется в индексе, пока его не уберут из отслеживания отдельной корректной операцией.
- Публично отправленный credential следует считать скомпрометированным и отозвать/перевыпустить. Переписывание истории — отдельная координационная операция, оно не отменяет уже скопированные данные.
- Пароли и ключи не помещают в исходники, Docker build args или доступные всем журналы.

## Уровень 1: рекомендуемый смысловой порядок

1. Наблюдаемый дефект: одинаковый commit, разная среда — отделить «код» от «условий выполнения».
2. Docker model: build-time vs run-time; image vs container; объяснить kernel boundary.
3. Storage model: writable layer vs bind mount vs volume; показать последствия удаления.
4. Dev Container: workflow студента и минимальная карта конфигурации.
5. Git model: три состояния и команды инспекции перед изменением.
6. Team workflow: branch → commit → fetch/pull/push; базовая модель divergence.
7. Hygiene: ignore build outputs, проверить stage, не коммитить секрет.
8. Применение к ROS 2: общий Jazzy-контейнер и отдельный Humble-контейнер робота.

## Минимальный технический walkthrough

Docker CLI запускается в хостовом терминале, если этот терминал имеет доступ к daemon:

```bash
docker run --rm -it ubuntu:24.04 bash
```

Внутри контейнера команда `cat /etc/os-release` показывает окружение образа. После `exit` временный контейнер удаляется; повторный запуск создаст новый экземпляр из образа.

Git walkthrough в репозитории уровня 2:

```bash
git status --short
git diff
git add README.md
git diff --staged
git commit -m "Добавил описание модели"
git log --oneline --decorate -3
```

Ожидаемый результат: до `add` изменения видны как unstaged; после `add` — в staged diff; после `commit` рабочая копия чистая, а вершина ветки указывает на новый commit.

## Ошибки, которые следует специально разобрать

1. Перепутать build-time (создание image) с runtime (запуск container).
2. Считать, что все данные внутри контейнера переживут удаление экземпляра.
3. Называть bind mount Docker volume.
4. Считать, что `git commit` сохраняет любые изменения из рабочей копии без staging.
5. Ждать, что `.gitignore` скроет ранее добавленный в Git файл.
6. Считать `git pull` синонимом `fetch`, забывая о последующей интеграции.
7. Считать удаление секрета из последнего коммита достаточной реакцией на его публикацию.
